# CNN scoring

**Audience:** users and developers. This is what distinguishes gnina from smina.

## How a complex becomes a 3D image

gnina represents the protein–ligand complex as a 3D image: atoms are rendered as gaussian densities on
a grid, generated by the libmolgrid library. The defaults are **0.5 Å resolution** over a
**23.5 Å cube**, which is 48 points per side, with separate channels per atom type — receptor and ligand
atoms are typed differently, so the network can tell them apart.

Both numbers are per-model, not global: they come from JSON metadata embedded in each `.pt` file and
default only if absent (see `torch_model.cpp:60-61`, and
[gninasrc/lib/models/README.md](../../gninasrc/lib/models/README.md) for the contract).

**This box size is a real limitation.** A ligand much larger than about 20 Å across will start to see
artefacts, because it no longer fits comfortably inside the grid. If you are docking macrocycles,
peptides or other extended molecules, treat the CNN scores with suspicion. `[Workshop2021]`

That grid is pushed through 3D convolutional layers — the same idea as 2D image-recognition CNNs,
learned filters building up from simple local features to higher-order structure — to produce two
numbers per pose `[CNN2017]`, `[GNINA1.0]`:

- **`CNNscore`** — the pose score, in [0, 1]. Trained with cross-entropy to classify whether the pose
  is within 2 Å RMSD of the true pose. This is what all pose optimization and the default ranking use.
- **`CNNaffinity`** — predicted binding affinity in pK units. Trained with a mean-squared error loss
  that is hinged when the pose is inaccurate, so a bad pose is not penalized for having a low
  predicted affinity.

For pK, roughly: 6 ≈ 1 µM, 9 ≈ 1 nM. Useful for ranking; not an exact predicted Kd.

There is also a derived **`CNN_VS`** field in the output, and an ensemble **variance**. See
[output-and-ranking.md](output-and-ranking.md).

## How to read a CNNscore

The "probability the pose is within 2 Å" reading is approximately right, and `[GNINA1.0]` measured how
approximately. Both halves of this matter:

**A high CNNscore means what you would hope.** Above 0.8, the top pose is within 2 Å about **79% of the
time when redocking** and about **56% of the time when cross-docking**. Higher thresholds are cleaner
still, but leave few poses.

**A low CNNscore is normal in prospective work.** 87% of redocking top poses clear 0.8 — but only
about **15%** of cross-docking ones do. So on a real target with a non-cognate receptor, most of your
poses will *not* have a confident score. That is the model correctly reporting that cross-docking is
hard, not a sign your setup is broken.

Read together: CNNscore is a usable confidence signal, its absolute scale is task-dependent, and you
should compare scores within a run rather than against a remembered threshold from a redocking
exercise.

## Ensembles

Evaluating several independently-trained models and averaging their outputs measurably beats any single
model — this held in every comparison across both papers `[GNINA1.0]`, `[GNINA1.3]`. It also gives you a
**variance** across the ensemble as a rough confidence signal: lower variance means the models agree.

The cost is linear in the number of models, and it hurts most exactly where you can least afford it:
CPU-only screening. GNINA 1.0's ensemble took 458 s per complex without a GPU versus 72 s for a single
model `[GNINA1.3]`. Solving that is what knowledge distillation is for.

## Knowledge distillation

This is the headline model work in GNINA 1.3, and it is what makes the `--cnn` model list
comprehensible.

**Knowledge distillation** trains a small "student" model to reproduce a large "teacher" model's
behaviour, so you get most of the teacher's quality at the student's cost. **Ensemble** distillation
does this with several teachers at once. `[GNINA1.3]`, `[KD2024]`

gnina's version: because default docking only uses the pose score, distillation targets the pose score
only. The loss is the sum of the KL divergence between the student's and each teacher's *pre-softmax*
pose-score logits, added to the ordinary ground-truth pose-classification and affinity losses. Training
uses the same dataset as the teachers.

The result: **distilled single models are not as good as the full ensemble they came from, but they are
better than any single undistilled model** — at one model's inference cost. Six distilled scoring
functions were produced this way.

Two of them are in the current default ensemble, and one of them *is* `--cnn fast`.

## Model families: decoding the names

`gnina --help` lists 66 accepted `--cnn` values. They are not arbitrary; the name encodes
architecture, training set, and provenance `[GNINA1.0]`, `[GNINA1.3]`:

| Name part | Meaning |
|---|---|
| `default2018` | The "Default 2018" architecture: a linear CNN, 5 convolutional layers |
| `dense` | The "Dense" architecture: 12 convolutional layers in 3 densely-connected blocks |
| `default2017` | The original 2017 architecture `[CNN2017]`; the only model with no seed variants |
| `crossdock_` | Trained on the full CrossDocked2020 dataset `[CrossDocked]` |
| `redock_` | Trained on ReDocked2020, the redocked-only subset |
| `general_` | Trained on a general set including PDBBind |
| `_1_3` | Retrained on **CrossDocked2020 v1.3**, which fixed misalignment and bond-typing errors |
| `_KD`, `_PT_KD` | **Knowledge-distilled** from the corresponding 5-variant ensemble |
| `all_default_to_default_1_3_*` | Distilled from the "All Default2018 Ensemble" — every Default2018-architecture model |
| trailing `_1` … `_4` | **Random-seed variants**, not quality ranks. Same data, same architecture, different initialization |

On the seed variants: the unsuffixed name (e.g. `dense`) is the best-performing variant of its group,
and `_1` through `_4` are the others `[GNINA1.0]`. So `dense_3` is not "better than `dense_2`" — they
are siblings.

> *This table describes 64 bundled `.pt` files plus two aliases.* It will go stale. Regenerate the
> authoritative list with `gnina --help`, or `ls gninasrc/lib/models/*.pt`.

## Choosing a model

Three names do the work for most people:

| Invocation | Resolves to | When |
|---|---|---|
| *(nothing)* | 3 models: `dense_1_3`, `dense_1_3_PT_KD_3`, `crossdock_default2018_KD_4` | Default. Best accuracy per unit time for one-off docking |
| `--cnn fast` | 1 model: `all_default_to_default_1_3_1` | High-throughput screening, and anything CPU-only |
| `--cnn default1.0` | 5 models: `dense`, `general_default2018_3`, `dense_3`, `crossdock_default2018`, `redock_default2018_2` | Reproducing GNINA 1.0 results |

> *Changed since 1.0:* the default is 3 models, not 5. Both were chosen by the same greedy
> forward-selection procedure over redocking and cross-docking performance; the 1.3 ensemble is both
> more accurate at cross-docking and faster. See [performance.md](performance.md).

The 1.3 default is a retrained dense model plus two distilled models — one dense, one
crossdock_default2018 — all trained on the full CrossDocked data. `[GNINA1.3]`

Note a small discrepancy if you are comparing against the paper: `[GNINA1.0]` names
`redock_default2018` as the fifth member of the 1.0 ensemble, while the code's `default1.0` alias uses
`redock_default2018_2`.

`--cnn` is multi-valued, so you can name several models explicitly:

```bash
gnina ... --cnn crossdock_default2018 dense_3
```

The `fast` and `default1.0` aliases only expand when they are the *only* value given —
`--cnn fast dense_3` fails with "Invalid model name: fast".

### `PREFIX_ensemble`, and a gotcha

`--cnn <prefix>_ensemble` evaluates every model whose name starts with `<prefix>`. This is a plain
prefix match over all 64 names, and the model set has grown a lot since the convention was introduced:

> **Watch out** — in GNINA 1.0, `--cnn dense_ensemble` meant 5 models. Today it matches `dense`,
> `dense_1`–`dense_4`, `dense_1_3`, `dense_1_3_1`–`_4`, `dense_1_3_PT_KD` and its variants, and
> `dense_1_3_PT_KD_def2018` and its variants — 18 models, and a correspondingly larger bill. Check
> `gnina --help | grep '^ *dense'` before assuming what a prefix expands to.

### Custom models

`--cnn_model <file.pt>` loads a TorchScript model from disk, and is also multi-valued. Built-in names
and external files can be combined; all are loaded. Packaging your own model is covered in
[developing.md](developing.md).

## `--cnn_scoring`: where the CNN is used

This controls *where in the pipeline* the CNN gets applied, which dominates runtime far more than which
model you pick.

| Value | Behaviour |
|---|---|
| `none` | Empirical scoring only, throughout. The pipeline becomes essentially smina |
| `rescore` | **Default.** CNN used only to score and re-rank the final pool of refined poses |
| `refinement` | CNN also used to locally minimize poses after the Monte Carlo search. ~10× `rescore` |
| `metrorescore` | Metropolis + rescore |
| `metrorefine` | Metropolis + refine |
| `all` | CNN used as the scoring function throughout the entire search |

Aliases the help text does not mention: `no` for `none`, `docking` for `all`, and anything starting
with `refine` or `min` for `refinement`.

**Why `rescore` is the default, and why that is a slightly deflating story.** `[GNINA1.0]` evaluated
`refinement` against `rescore` and found the TopN curves essentially overlapping — CNN-guided
refinement costs an order of magnitude more for no meaningful accuracy gain. Given the effort invested
in CNN scoring, that is a disappointing result; the silver lining is that skipping CNN-guided
refinement is exactly what makes the default mode cheap. `[Workshop2021]`

`all` is slower by orders of magnitude and was never completed on the benchmark set in reasonable time
`[GNINA1.0]`. The reason is structural: during sampling the empirical function is evaluated through a
precalculated per-atom grid approximation, but a CNN score is not additive over atoms, so no equivalent
shortcut exists — every mutation in every chain needs a full forward pass. Do not use `all` for routine
work.

**`--cnn_scoring none` has a side effect worth knowing:** it silently forces
`--pose_sort_order Energy`, regardless of what you passed. That is sensible — there is no CNN score to
sort by — but it means the flag changes more than the scoring. See
[output-and-ranking.md](output-and-ranking.md).

## GPU or not

A GPU matters a lot here: `[Workshop2021]`'s example was a run that took 11 s on GPU and over two
minutes on CPU. But that was the Caffe era. The PyTorch migration in 1.3 cut CPU-only docking from
129 s to about 30 s per complex, and distillation cut it further — `--cnn fast` now costs about 16 s,
only 1.3 s more than Vina empirical scoring alone, and under 1 s more than the same model on a GPU
`[GNINA1.3]`.

So CPU-only CNN scoring is now genuinely practical, provided you pick the right model. Numbers in
[performance.md](performance.md); the mechanics of running without a GPU at all are in
[install.md](install.md).

Note also that `--device` is ignored by the PyTorch backend — use `CUDA_VISIBLE_DEVICES`.

  [make_model_cpp.py](../../gninasrc/make_model_cpp.py) from the `.pt` list in
  [gninasrc/CMakeLists.txt](../../gninasrc/CMakeLists.txt). Note that
  [cnn_data.cpp](../../gninasrc/lib/cnn_data.cpp) looks like the registry but is **dead code** — it is
  not in `LIB_SRCS` and nothing references it; it is a Caffe-era leftover whose model list and
  `crossdock_default2018` default are both obsolete.
